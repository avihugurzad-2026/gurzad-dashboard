שלב 2: כסף, משתמשים ויומן דו-כיווני
מטרה: לאפשר לעדן להתחבר, לשלוט בהרשאות, לנהל הכנסות והוצאות בצורה שתואמת לישראל, וליצור אירועים ביומן מתוך המערכת.
2.1 משתמשים והרשאות
תפקידים (Roles):

* Owner: שליטה מלאה במערכת ובהרשאות.
* Admin: ניהול ישויות ומשתמשים, ללא מחיקת נתונים משותפים.
* Manager: ניהול סניף או ישות ספציפית.
* Employee: רואה ומעדכן משימות שהוקצו לו.
* Viewer: קריאה בלבד.

טבלאות נוספות:

* `workspace_members`: user_id, entity_id (או area_id), role. מאפשר הרשאה לפי ישות, למשל עובד שרואה רק Head Spa → מודיעין.
* `invitations`: email, role, entity_id, token, expires_at, accepted_at.

זרימה:

1. Owner שולח הזמנה למייל של עדן עם תפקיד ו-Scope.
2. עדן נרשמת ומקבלת גישה רק למה שהוגדר.
3. כל שאילתה במערכת מסננת לפי `owner_user_id`, `scope`, ו-`workspace_members`. חשוב: הסינון נעשה בשרת ובמסד הנתונים, לא רק בממשק.

Scope:

* `user`: רשומה פרטית של המשתמש.
* `shared`: רשומה שרואים כל המשתמשים שיש להם גישה לישות.

דוגמה: משימה "לשלם ביטוח רכב" עם `scope = shared` שייכת לאישי, ועדן רואה אותה. משימה "לבדוק הצעת מחיר של מודיעין" עם `scope = user` נשארת אצל אביהו.
2.2 חיבור דו-כיווני ליומן Google
זו הפונקציה שביקשת לחיבור מלא, וכך היא עובדת:
חיבור ראשוני (לכל משתמש בנפרד)

1. המשתמש לוחץ "חבר יומן Google" בהגדרות.
2. המערכת פותחת את מסך ההרשאה של Google (OAuth 2.0) עם scopes של קריאה וכתיבה ליומן בלבד.
3. לאחר האישור נשמרים refresh token מוצפן ורשומת `calendar_connections`.
4. המערכת מציגה את כל היומנים שיש למשתמש (אישי, עבודה, משפחה, יומנים משותפים).

מיפוי יומנים לישויות

* לכל יומן ניתן לשייך Entity או Branch, או להשאיר אותו "אישי כללי".
* דוגמה: יומן "מודיעין" → Head Spa → מודיעין. יומן "אישי" → אישי.
* אירוע שמגיע מיומן ממופה נשמר עם `entity_id` ו-`branch_id` בהתאם.

סנכרון נכנס (Google → המערכת)

* סנכרון ראשוני מלא בחיבור הראשון.
* לאחר מכן סנכרון מצטבר לפי `sync_token`, כך שרק שינויים נשלפים.
* הרשמה ל-Push Notifications (Watch Channel) של Google, עם חידוש תקופתי של ה-channel לפני פקיעתו.
* גיבוי: סנכרון polling כל 15 דקות למקרה שההתראות נכשלו.
* אירוע שנמחק ביומן נמחק מהמערכת (soft delete עם `deleted_at`).

סנכרון יוצא (המערכת → Google)

* יצירה ועריכה של אירוע מתוך המערכת נשלחות ל-Google ומקבלות `google_event_id`.
* משימה עם תאריך ושעה יכולה להיות מסומנת "הצג ביומן", ואז נוצר אירוע ביומן.
* כלל התנגשויות: עריכה אחרונה מנצחת (last-write-wins לפי `updated_at`). אם שני הצדדים השתנו באותו זמן, המערכת מציגה את שני הגרסאות ושואלת את המשתמש.

טיפול בשגיאות

* אם ה-refresh token פג או בוטל, הסטטוס משתנה ל-`error` והמשתמש מקבל התראה לחבר מחדש.
* כל כשל סנכרון נרשם ב-`activity_log`.

פרטיות ואבטחה

* טוקנים נשמרים מוצפנים בשרת, לא בדפדפן.
* המשתמש יכול לנתק את החיבור בכל רגע, והמערכת מוחקת את הטוקן.

הערה לגבי אישור Google: לשימוש פרטי או לחשבונות מוגדרים בפרויקט Google Cloud, החיבור עובד ללא תהליך אימות מיוחד. אם המערכת תיפתח לציבור, Google עשויה לדרוש אימות של האפליקציה בגלל הרשאות יומן.
2.3 מודול פיננסים
Dashboard פיננסי

* הכנסות והוצאות לפי תקופה (היום, שבוע, חודש, רבעון, שנה, טווח מותאם).
* פילוח לפי קטגוריה וישות.
* חלוקה ברורה בין עסקי לאישי.

שדות עסקה (`transactions`)

* direction: הכנסה / הוצאה
* amount_gross (סכום כולל)
* vat_included (כן / לא)
* vat_amount (מחושב אוטומטית לפי שיעור המע"מ שמוגדר במערכת לפי תאריך העסקה)
* document_type: חשבונית מס / קבלה / חשבונית מס-קבלה / חשבונית עסקה / אחר / ללא מסמך
* document_number
* counterparty_name
* counterparty_tax_id (ח.פ., ע.מ., או ת.ז.)
* payment_method (העברה / כרטיס / מזומן / צ'ק / אחר)
* payment_date
* entity_id, branch_id
* classification: עסקי / אישי / מעורב
* owner_user_id, scope
* split: אם ההוצאה משותפת, נשמרות הפרופורציות לכל משתמש (למשל 50/50)

דוחות

* סיכום מע"מ חודשי: מע"מ עסקאות מול מע"מ תשומות.
* ייצוא CSV לרואה החשבון עם כל השדות.
* סיכום לפי ישות ולפי סניף.

הערה: את הדרישות המדויקות לדיווחים מול רשות המסים כדאי לאשר עם רואה החשבון לפני שמגדירים את שדות החובה.
2.4 גבייה (a-digital)

* רשומת `receivables` לכל חוב: לקוח, סכום, תאריך יעד, סטטוס (ממתין / באיחור / שולם / חלקי), וקשר לחשבונית.
* תצוגה כטבלה: לקוח, סכום, תאריך יעד, ימי איחור, סטטוס.
* פילטרים: הכל, באיחור, השבוע, שולם, ממתין.
* ימי איחור מחושבים אוטומטית מתאריך היעד.

2.5 Inbox חכם

* כשמעלים קובץ בלי סיווג, המערכת שואלת: "למה המסמך הזה שייך?" ומציגה את האפשרויות: אישי, a-digital, Head Spa, יזמות.
* לאחר מכן בוחרים Category.
* ההצעה מבוססת על הסיווג האחרון שהמשתמש עשה לקבצים דומים (למשל קבלות מספק מסוים).

2.6 יעדים (Goal Engine בסיסי)

* טבלת `goals`: name, target_value, current_value, unit, due_date, owner_user_id, scope, entity_id, branch_id, notes.
* סוגים: אישי, עסקי, סניף, פיננסי, לימודים, יזמות.
* Progress Bar לכל יעד.

2.7 קריטריוני קבלה לשלב 2

* עדן מתחברת, רואה רק את מה שהוגדר לה, ויכולה להוסיף משימה משותפת.
* אירוע שנוצר במערכת מופיע ביומן Google, ואירוע שנוצר ביומן Google מופיע במערכת תוך דקות.
* הוצאה עם מע"מ מחושבת נכון, וייצוא CSV מכיל את כל השדות.
* גבייה מציגה ימי איחור נכונים ומתעדכנת כששולם.

שלב 3: הרחבה לנכסים, סניפים, מסמכים ו-API
מטרה: להוסיף את שאר התחומים בלי לשנות את המבנה שנבנה בשלבים הקודמים.
3.1 Head Spa Israel: מבנה מלא

* Company Overview: Aggregate של כל הסניפים: הכנסות היום והחודש, מספר טיפולים, Average Ticket, לקוחות, ביטולים, יעדים.
* ביצועים לפי סניף: מודיעין (פעיל), ירושלים (טרם פעיל).
* Branch Dashboard Component אחד: כל סניף נטען עם `branch_id` ולא עם קוד נפרד. סניף שלישי נוסף בהגדרה בלבד.

3.2 חיבור BUYZ API למודיעין

* טבלת `integrations`: provider, entity_id, branch_id, credentials_encrypted, status, last_sync_at.
* משיכה מתוזמנת של מכירות, הזמנות ולקוחות לטבלאות המקומיות.
* מסכי מודיעין: מכירות, טיפולים / הזמנות, לקוחות, צוות.
* לוגים של כל סנכרון ב-`activity_log`.
* ירושלים משתמשת באותו Dashboard. כשיתחבר מקור נתונים, המסך יתמלא בלי שינוי קוד.

3.3 Ventures (יזמות)

* נכסים: כל נכס הוא Entity בפני עצמו, עם שווי, עלות רכישה, הכנסות, הוצאות, הלוואות, תשואה, מסמכים, חוזים ואנשי קשר.
* השקעות: קטגוריה, סכום השקעה, שווי נוכחי, תשואה, תאריך, מסמכים, הערות, משימות קשורות. הבסיס מאפשר אינטגרציה לשוק ההון בעתיד.
* משפטי: כל Case הוא Object עם סטטוס, צדדים, עורך דין, תאריכים, משימות, מסמכים, תשלומים, Deadlines ו-Notes.

כלל לגבי נכסים ומימון: נכס שמומן בהלוואה מופיע ביזמות. ההלוואה עצמה נשמרת כ-`liabilities` ומקושרת לנכס. חשבון הבנק שממנו משלמים את ההחזר נשאר באזור האישי, והתשלום נרשם בשתי הישויות לפי הפרופורציה שנקבעה ב-`split`.
3.4 מסמכים (מערכת אחת)

* כל מסמך שייך ל-Area, Entity ו-Branch (אופציונלי).
* סוג מסמך: חשבונית, קבלה, חוזה, מסמך משפטי, דוח, אחר.
* אחסון בתוך המערכת עם גרסאות בסיסיות.
* חיפוש לפי שם, סוג, ישות ותאריך.

3.5 חיפוש גלובלי (⌘K)

* חיפוש אחד על משימות, לקוחות, מסמכים, ישויות, סניפים, יעדים, נכסים והשקעות.
* תוצאות מקובצות לפי סוג ומציגות Breadcrumb.

3.6 Activity Log מלא

* כל פעולה משמעותית נרשמת: מי, מתי, על איזה אובייקט, ומה עשה.
* תצוגה במסך נפרד ובפרופיל של כל ישות.

3.7 Global Filters וסיכומים

* סינון לפי תקופה ו-Workspace/Entity/Branch בכל מסך רלוונטי.
* "Business Snapshot" בדשבורד הראשי: כרטיס לכל עסק (הכנסה היום, החודש, משימות דחופות).
* "Personal Snapshot": הוצאות החודש, משימות השבוע, אירועים, יעד פיננסי.
* Home הופך ל-CEO Dashboard אמיתי.

3.8 עיצוב וטיפוגרפיה סופיים

* היררכיית טקסט: Page Title 28–32px (600–700), Section Header 20–22px (600), Card Heading 15–17px (600), KPI 28–34px (600–700), Body 15–16px (400), Secondary 13–14px (400), Sidebar 14–15px (500).
* פונט: Google Sans / Google Sans Text כשיש קבצי רישיון בפרויקט. עד אז Inter או Roboto.
* RTL מלא: אייקונים, Dropdowns, טבלאות, Breadcrumbs, גרפים, Progress, תאריכים ומטבע (₪) מותאמים לעברית.

3.9 קריטריוני קבלה לשלב 3

* סניף שלישי נוסף באמצעות הגדרה בלבד, בלי שינוי קוד.
* נתוני מודיעין מגיעים מ-BUYZ ומופיעים בדשבורד הסניף.
* נכס עם הלוואה מציג נכון את ההחזרים ואת התשואה.
* חיפוש ⌘K מוצא אובייקט מכל סוג בפחות משנייה.
